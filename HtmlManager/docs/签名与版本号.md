# 签名与版本号

> 两个曾经靠人手记、现在交给机器的事：包内版本号每次提交必然递增；
> 发布包用正式密钥签名，密钥不进仓库。

## 一、版本号

| 项 | 规则 |
| --- | --- |
| `versionCode` | `git rev-list --count HEAD`，即当前分支的提交总数 |
| `versionName`（日常） | `1.2.<versionCode>`，如 `1.2.7` |
| `versionName`（tag） | tag 名去掉 `v`，如打 `v1.3.0` 得到 `1.3.0` |

实现在 [`app/build.gradle.kts`](../app/build.gradle.kts)：

```kotlin
val commitCount: Int = providers.gradleProperty("appVersionCode").orNull?.toIntOrNull()
    ?: gitCommitCount()
val appVersionName: String = providers.gradleProperty("appVersionName").orNull?.takeIf { it.isNotBlank() }
    ?: "1.2.$commitCount"
```

`versionCode` 用提交数而不是时间戳，理由：

- 单调递增（只要不 rebase 改写历史），系统升级比较认这个
- 一眼能对出「这个包是仓库第几次提交」，排查线上问题时比递增序号有用
- 不需要额外文件记当前版本，也就不存在「忘了改」

`-PappVersionCode` / `-PappVersionName` 可以覆盖，覆盖值优先。CI 打 tag 时用 `-PappVersionName=<tag>`，
让 Release 名和包内版本号对得上。

**已知边界**：rebase、squash 之后提交数会变小，`versionCode` 可能倒退。发布分支上别改历史，
或者届时用 `-PappVersionCode` 手工兜一次。

构建中随时可以查当前生效的版本：

```bash
./gradlew -q printVersion
# versionCode=6 versionName=1.2.6 signing=debug
```

## 二、签名

### 密钥材料的四个变量

| 变量 | 内容 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | keystore 文件内容的 base64（CI 用） |
| `ANDROID_KEYSTORE_FILE` | keystore 文件路径（本地用；CI 会自己解出 base64 再填这个） |
| `ANDROID_KEYSTORE_PASSWORD` | store 密码 |
| `ANDROID_KEY_ALIAS` | key 别名 |
| `ANDROID_KEY_PASSWORD` | key 密码 |

Gradle 侧先读环境变量，读不到再读 `.ci/signing.properties`（该文件已 `gitignore`）。
四项齐全且 keystore 文件存在才启用 release 签名，否则 `assembleRelease` 退回无签名配置、
构建脚本退回 `assembleDebug`——**能装、能测、上不了架**，不会把流水线卡死。

### 生成一份密钥

```bash
bash .ci/setup-signing.sh
```

脚本会做三件事：生成 `release.jks`（RSA 2048，有效期 30 年）、随机密码、
打印一份可直接粘进密钥仓库的 YAML。**keystore 文件自己留好，丢了就再也签不出同一个身份。**

想手工生成：

```bash
keytool -genkeypair -v -keystore release.jks -alias htmlmanager \
  -keyalg RSA -keysize 2048 -validity 10950
```

### 配进流水线

密钥仓库只能在平台网页上创建（禁止 clone、禁止本地 push），步骤：

1. 平台右上角 `+` → 创建仓库 → 类型选 **密钥仓库**，名称如 `djzrs/android-signing`
2. 在网页里新建 `html-manager-signing.yml`，内容为脚本打印出的那一段：
   ```yaml
   ANDROID_KEYSTORE_BASE64: "MIIK..."
   ANDROID_KEYSTORE_PASSWORD: "..."
   ANDROID_KEY_ALIAS: "htmlmanager"
   ANDROID_KEY_PASSWORD: "..."

   # 只允许本仓库的 main / tag 流水线引用
   allow_slugs:
     - djzrs/AndriodCloudBuild
   allow_events:
     - push
     - tag_push
   ```
3. 把 [`.cnb.yml`](../../.cnb.yml) 里 `html-manager-build` 的 `imports` 换成该文件地址：
   ```yaml
   imports:
     - https://cnb.cool/djzrs/android-signing/-/blob/main/html-manager-signing.yml
   ```

现在指向的是仓库内的占位文件 [`signing.yml`](../.ci/signing.yml)，四项为空，所以构建走 debug 签名。
占位文件必须留着——`imports` 指向不存在的文件会在 Prepare 阶段直接失败，连编译都跑不起来。

`allow_events` 写 `push`/`tag_push` 而不是留空，是因为密钥文件一旦被 PR 流水线引用，
PR 的作者就能改 `.cnb.yml` 把密钥 echo 到日志里。密钥只给可信事件。

### 本地用同一份密钥

```bash
cat > .ci/signing.properties <<PROP
keystoreFile=/absolute/path/release.jks
keystorePassword=xxx
keyAlias=htmlmanager
keyPassword=xxx
PROP
```

本地出正式包：

```bash
./gradlew assembleRelease
# 产物：app/build/outputs/apk/release/app-release.apk
```

### 验证签名对不对

```bash
$ANDROID_SDK_ROOT/build-tools/34.0.0/apksigner verify --print-certs app-release.apk
```

带签名的包，流水线日志里会自动打出 SHA-256 指纹。**第一次发出去的包，指纹记下来**——
以后换设备、换密钥时，指纹不一致系统会拒绝覆盖安装，那时候就知道是新密钥了。

## 三、debug 与 release 的区别

| | debug | release（已配密钥） |
| --- | --- | --- |
| 签名 | 构建机自动生成的 debug 密钥 | 你的密钥 |
| 可安装 | 是 | 是 |
| 可上架 | 否 | 是 |
| 可覆盖升级已有安装 | 取决于签名是否一致 | 取决于签名是否一致 |

debug 密钥每台机器不同，所以「同事装的包」和「CI 出的包」签名不同，互相覆盖安装要先卸载。
换成固定密钥之后这个问题就没了。
