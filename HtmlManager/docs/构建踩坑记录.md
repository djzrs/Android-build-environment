# 构建踩坑记录

> 这份文档只记「踩过一次、下次还会踩」的事。每条都写清现象、原因、怎么绕过去。
> 时间顺序从上往下，新的追加在末尾。

## 1. Maven Central 对构建节点返回 429

**现象**：`./gradlew assembleDebug` 跑两三分钟后全线失败，错误清一色是：

```
Could not GET 'https://repo.maven.apache.org/maven2/org/jetbrains/annotations/13.0/annotations-13.0.pom'.
Received status code 429 from server: Too Many Requests
```

**原因**：`repo.maven.apache.org` 对平台出口 IP 限流。连裸 `curl` 请求一次也是 429，
跟并发、跟 Gradle 配置都无关。同环境下 `dl.google.com` 与 `plugins.gradle.org` 都正常。

**处理**：`settings.gradle.kts` 里把阿里云镜像插到仓库列表前面，官方源保留作回落。

```kotlin
repositories {
    maven("https://maven.aliyun.com/repository/google")
    maven("https://maven.aliyun.com/repository/public")
    google()
    mavenCentral()
}
```

**验证**：阿里云 `google` / `public` / `gradle-plugin` 三个仓都能直接取到
AGP 8.5.2、Kotlin 1.9.24 插件、nanohttpd 2.3.1 的 pom，改完本地编译通过。

早期是在 `~/.gradle/init.gradle` 里做全局注入绕过去的，那只对当次构建有效，
换个构建节点就复现，所以最后落在仓库配置里。

## 2. 构建环境里没有 JDK 也没有 Android SDK

**现象**：`./gradlew` 直接报 `JAVA_HOME is not set`，装上 JDK 之后报
`SDK location not found`。

**原因**：平台缺省构建镜像 `cnbcool/default-build-env` 只带 git / curl / jq 这类基础工具，
Android 编译链一个都没有。

**处理**：写 [`.ci/android.Dockerfile`](../.ci/android.Dockerfile)，
装 JDK 17 + commandline-tools + `platforms;android-34` + `build-tools;34.0.0`，
用 `docker.build` 引用。装一次就缓存在制品库，后面每轮直接复用。

`local.properties` 不提交（`.gitignore` 挡着），`.ci/build.sh` 里用镜像的
`ANDROID_SDK_ROOT` 现写一份，这样本地开发和 CI 两条路都能走通。

## 3. NanoHTTPD 用字符串响应会截断中文

**现象**：`/files/中文名.html` 在浏览器里只显示前半截。

**原因**：`newFixedLengthResponse(status, mime, String)` 的 `Content-Length` 按**字符数**
算，而浏览器按**字节数**读。一个汉字三字节，中文越多截得越狠。

**处理**：`AppHttpServer.serveFile` 改成读 `ByteArray` 再走 `ByteArrayInputStream`，
长度取 `bytes.size`。

## 4. Android 11+ 不声明 `<queries>` 就查不到浏览器

**现象**：预览永远弹「未找到可用的浏览器」，但机器上明明装了 Chrome。

**原因**：Android 11 起包可见性收紧，`resolveActivity` 对未声明的 intent 一律返回 null。

**处理**：Manifest 里补声明：

```xml
<queries>
    <intent>
        <action android:name="android.intent.action.VIEW" />
        <data android:mimeType="text/html" />
    </intent>
</queries>
```

## 5. `content://` 打开时相对路径资源加载失败

**现象**：HTML 里 `<link href="style.css">` 在系统浏览器里不生效。

**原因**：`FileProvider` 只授权了单个文件 URI，同目录下的 CSS / JS / 图片拿不到读权限。
这是浏览器侧的限制，不是本应用的 bug。

**处理**：不处理。文档里写明「建议使用自包含单文件 HTML」，这也是服务器功能存在的理由——
走局域网 HTTP 访问时，资源按正常路径请求，相对引用是好的。

## 6. 平台底包是 Debian trixie，`openjdk-17` 已经不在源里

**现象**：CI 里镜像构建挂在第二步：

```
E: Unable to locate package openjdk-17-jdk-headless
```

**原因**：`cnbcool/default-build-env` 的底包是 Debian trixie（不是 bookworm）。
trixie 源里只有 `openjdk-21-*`，17 已经移除。本地开发机是 bookworm，装得上 17，所以本地发现不了。

**处理**：Dockerfile 改用 `openjdk-21-jdk-headless`。工程的 `jvmTarget` 还是 17，
用 21 的 javac 编 17 字节码是支持的，本地实测 `clean assembleDebug` 通过、APK 能装。

`JAVA_HOME` 没写死 `/usr/lib/jvm/java-17-openjdk-amd64` 这类路径——换个发行版或架构就失效。
改成从 `command -v javac` 反推：

```dockerfile
ln -sfn "$(dirname "$(dirname "$(readlink -f "$(command -v javac)")")")" /opt/java-home
ENV JAVA_HOME=/opt/java-home
```

## 7. `git:release` 建 Release，`attachments` 挂附件，两步必须有序

**现象**：把上传附件写在了创建 Release 前面，报 `NO_RELEASE_ID`。

**原因**：`cnbcool/attachments` 上传 release 附件前会先按 tag 查 release id，
查不到就直接退出；而 release 是 `git:release` 建的。

**处理**：`git:release` 在前，附件上传在后。

另外一个容易忽略的点：`tag_push` 事件里 `attachments` 不用传 `tag`，
插件会自动取 `$CNB_BRANCH`；但 `push` 事件上传 release 附件必须显式传 `tag`，
否则会当成 commit 附件，跑到提交详情页上去。

## 8. 用 `--config` 自测，别为试一次就推一次

**现象**：想验证发布链路，但改动还没合入 main，main 的提交里没有 `.ci/android.Dockerfile`，
提示 `docker.build.dockerfile is not found`。

**处理**：`cnb build start-build` 支持 `--config` 整体替换流水线配置，
把新配置指向当前分支、事件用 `api_trigger`，就能在合并前把整条链路跑通：

```bash
cnb build start-build --repo djzrs/AndriodCloudBuild \
  --branch feat/xxx --event api_trigger --title "自测" \
  --config "$(cat selftest.yml)"
```

自测会真的建 Release、真的推 tag，跑完记得清掉，否则会污染正式发布。
清理顺序是先删 Release 再删 tag：

```bash
curl -X DELETE "https://api.cnb.cool/<slug>/-/releases/<release-id>" -H "Authorization: Bearer $CNB_TOKEN"
curl -X DELETE "https://api.cnb.cool/<slug>/-/git/tags/<tag>" -H "Authorization: Bearer $CNB_TOKEN"
```

## 9. `imports` 指向不存在的文件，Prepare 阶段就挂，`allowFailure` 也救不回来

**现象**：为了「有密钥就签名、没有就跳过」，把 `imports` 指向一个还没建的密钥仓库地址，
结果整条流水线在 Prepare 阶段 error，`script` 一行都没跑，`allowFailure: true` 也没用。

**原因**：`imports` 在流水线启动前解析，属于 Prepare 阶段。这个阶段失败视作配置错误，
不进任务执行阶段，所以 `allowFailure` 管不到。

**处理**：留一个值为空的占位文件在仓库里，`imports` 指向它；等密钥仓库就绪后，
把 `imports` 换成密钥仓库地址，占位文件继续留着（不删，删了路径就断了）。

空值的效果是：环境变量存在但为空，构建脚本判定「材料不齐」→ 退回 debug 签名 → 构建成功。

**教训**：`imports` / `settingsFrom` / `optionsFrom` 这类引用，宁可指向「存在的空文件」，
不要指向「可能不存在的真文件」。两者失败时机不同，前者可控，后者直接挂。

## 10. 版本号用提交数，但 rebase 会让它倒退

**现象**：`versionCode = git rev-list --count HEAD`，一 rebase 少两个提交，
versionCode 从 8 变 6，系统装升级包时会报 `INSTALL_FAILED_VERSION_DOWNGRADE`。

**原因**：提交数依赖历史形状，改写历史就重新计数。

**处理**：发布分支不改历史。真需要时用 `-PappVersionCode=<更大的数>` 手工兜一次。
`versionName` 同理可以 `-PappVersionName` 覆盖，CI 打 tag 时就是这么干的。

## 11. `apksigner verify` 能验签，这说明签名真的生效了

**现象**：配好密钥、`assembleRelease` 成功，但不确定签名是否真进了包。

**处理**：`apksigner verify --print-certs app-release.apk` 看证书指纹。
`.ci/build.sh` 在有签名材料时会把前 5 行打进日志。

第一次发布时把 SHA-256 指纹记进项目文档。以后换密钥，指纹一变，老用户的覆盖安装就会失败，
这是「签名换了」最直接的证据。
